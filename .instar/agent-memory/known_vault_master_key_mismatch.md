They belong to Roland, not me." I.e. this vault holds low-value service credentials (Ambient Weather API keys, etc.), not Adrian's personal/financial secrets — the encryption ceremony isn't worth the operational fragility it's caused (5+ days of a broken morning report). Do NOT propose switching to a raw JSON file or re-litigate this without new information — it was a deliberate, informed tradeoff, not an oversight.

**Discovered 2026-07-12** while investigating why the 07:00 morning-weather report was missing indoor/pool temps and battery status. That report had already self-flagged: "the Ambient Weather vault couldn't be read this morning."

Some time between creation and the next morning, the keychain entry became unreadable/unavailable (background LaunchAgent context can't always prompt for keychain access), so `MasterKeyManager` fell through to the file path and generated a NEW key there — which does not match what encrypted the vault. Unverified; do not repeat as fact without checking `MasterKeyManager.getMasterKey()` behavior in the current dist.

**DO NOT repair, rotate, or delete the vault or key file** — per CLAUDE.md's explicit instruction on decrypt failures, this is surfaced to the operator (Adrian), not fixed unilaterally. A wrong move destroys stored secrets permanently.

**Root cause confirmed 2026-07-12** by calling `SecretStore.read()` directly: the raw error names the exact key id the vault needs (`65da56d91a42e645`) vs what's resolvable now (`file:18e9371561b89dda`) — a genuine, provable key mismatch, not corruption. Then confirmed WHY via `security list-keychains` / `find-generic-password` from this session context: the keychain search list here is ONLY `/Library/Keychains/System.keychain` — the user's login keychain (where the original master key almost certainly landed, written by the SERVER process which has a real GUI/login session) is unreachable ("User interaction is not allowed") from background job/session contexts. So: vault created 2026-07-08 16:18 via the server (had keychain access, wrote key to login keychain) → first read attempt next morning (2026-07-09 07:00, morning-weather job, a spawned session WITHOUT keychain access) failed to read that key, silently generated + wrote a NEW mismatched key to the file fallback. Every read since used the wrong key.

**Fixed 2026-07-12** (operator said "fix that"):
